Setup runbook

Wiring NoGhost to AWS

Two services, nothing to provision, one IAM role and two environment variables — neither of them a secret. About twenty minutes, most of it in the IAM console.

Rekognition
Runs a Face Liveness video check on funnel step 3, then compares the frame it returns to the first profile photo when the application is filed.
Without it: every applicant records liveness_passed = NULL — “no check ran” — and a person reviews them, which is where they were going anyway.
Location Places v2
Turns a typed postcode into a coordinate on funnel step 5, for anyone who declines the browser location prompt.
Without it: the field says the lookup isn’t switched on, and the “Use my location” button still works.

Neither service is load-bearing. Both stop work being done by hand.

Three things I checked, and what each one changed

You asked me to verify the steps before handing them over. These are the three that came back different from what I would have written from memory — each one changed the code, so the guide below is shorter than it would have been.

There is no AWS_PLACE_INDEX any more

The geocoder used SearchPlaceIndexForText, which is the v1 Places API. AWS files its reference under /location/previous/, states it “is no longer current and may be deprecated in the future”, and recommends Geocode instead. v1 also required standing up a place index resource before a single lookup could run. v2 has no resource at all — which is why step 2 below creates a policy and nothing else.

IntendedUse has to be Storage

It defaults to SingleUse, meaning “show this on a map and throw it away”. NoGhost writes the coordinate to profiles.lat/lng and keeps it, and AWS is explicit that storing a response without this flag breaks the terms of service. It bills at roughly eight times the single-use rate, which is the right trade against geocoding the same person on every screen that needs to know where they are.

OIDC is already switched on for noghost-web

Enabled, in team issuer mode. So there is nothing to toggle on the Vercel side, and every placeholder in AWS’s documentation has a real value below rather than a [TEAM_SLUG].

AWS_REGION is preset by Vercel

A function in sfo1 arrives with AWS_REGION=us-west-1 whether or not you set it — and us-west-1 carries neither service. Forgetting this variable therefore looks exactly like setting it, and the symptom is an endpoint error rather than “AWS isn’t configured”. lib/aws.ts now refuses a region that cannot serve us and says so. Vercel’s own documentation goes further: with multi-region routing the value “can change depending on which region your function runs in”.

Pick a region

Use us-east-1 unless you have a reason not to. Rekognition Face Liveness is in five regions only — far fewer than the rest of AWS, and since it is now the identity check rather than an extra, it sets the constraint:

us-east-1
us-west-2
eu-west-1
ap-northeast-1
ap-south-1
us-west-1

Amazon Location Places covers all five, so the intersection is just that list. Anywhere else — including us-east-2, which is fine for everything else — reaches the liveness call and finds no endpoint. lib/aws.ts refuses those up front rather than letting them fail mid-funnel. The struck-through one is what Vercel hands you by default from sfo1.

This is not the region picker in the AWS console. Every step below happens in IAM, which is a global service — so the selector in the top-right will read Global the whole way through, and that is correct rather than a problem to fix. You never need to switch it. AWS_REGION is a string you type into an environment variable, and it chooses which API endpoint gets called. The only other place the region appears is typed into the policy ARN in step 2.

Create the policy

IAM → Policies → Create policy → JSON tab. Paste this, changing the region in the ARN if you didn’t pick us-east-1. Name it noghost-app. 

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadFacesForVerification",
      "Effect": "Allow",
      "Action": [
        "rekognition:CreateFaceLivenessSession",
        "rekognition:StartFaceLivenessSession",
        "rekognition:GetFaceLivenessSessionResults",
        "rekognition:CompareFaces"
      ],
      "Resource": "*"
    },
    {
      "Sid": "GeocodeTypedPlaces",
      "Effect": "Allow",
      "Action": "geo-places:Geocode",
      "Resource": "arn:aws:geo-places:us-east-1::provider/default"
    }
  ]
}

Two details worth knowing rather than wondering about. The Rekognition actions take "*" because they have no resource type — there is nothing to scope them to. And the geo-places ARN really does have two colons before provider: the account-id segment is empty. If that gives you trouble, "Resource": "*" works and is barely less specific, since default is the only provider there is.

This policy grants three read actions and nothing else. It cannot create, delete, or spend beyond those calls.

Trust Vercel, and make a role

No access key. Vercel signs a short-lived token on every invocation, AWS trusts that issuer, and it is exchanged for credentials that expire in an hour. There is nothing persistent to leak and nothing to rotate.

Team slugkevin-bandisons-projects
Provider URLhttps://oidc.vercel.com/kevin-bandisons-projects
Audiencehttps://vercel.com/kevin-bandisons-projects
Subjectowner:kevin-bandisons-projects:project:noghost-web:environment:production

AWS’s documentation writes every one of those as [TEAM_SLUG]. These are yours.

a. Add the identity provider

IAM → Identity providers → Add provider → OpenID Connect, with the provider URL and audience above.

b. Create the role

A role is two things, and the wizard only gets one of them right. Who may assume it is the trust policy; what it may do is the permissions. You attach the permissions on the way through and come back to fix the trust policy.

IAM → Roles → Create role → Web identity, choosing the provider you just made and the audience alongside it. On the permissions screen tick noghost-app — the policy from step 2. Name the role noghost-app too, and create it.

Now open it: Trust relationships → Edit trust policy. The wizard writes one that checks only the audience, which every project on the team shares — so as created, any of the other nine could assume this role. Replace it with the below, putting your twelve-digit AWS account number in place of YOUR_ACCOUNT_ID: 

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::YOUR_ACCOUNT_ID:oidc-provider/oidc.vercel.com/kevin-bandisons-projects"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "oidc.vercel.com/kevin-bandisons-projects:aud":
            "https://vercel.com/kevin-bandisons-projects"
        },
        "StringLike": {
          "oidc.vercel.com/kevin-bandisons-projects:sub": [
            "owner:kevin-bandisons-projects:project:noghost-web:environment:production",
            "owner:kevin-bandisons-projects:project:noghost-web:environment:preview",
            "owner:kevin-bandisons-projects:project:noghost-web:environment:development"
          ]
        }
      }
    }
  ]
}

Three subjects, named one at a time rather than with a wildcard. Only noghost-web calls AWS — noghost-admin has no reason to, and nine other projects share this team. development is there so the same role works from your laptop; drop that line if you would rather local development had no AWS at all.

Save it, then copy the role ARN from the top of the page. It looks like arn:aws:iam::123456789012:role/noghost-app.

If your issuer mode says Global

The values above are for Team mode, which is what noghost-web is set to. Vercel’s other option is Global, and it changes the issuer — so the provider URL and the condition keys move, while the audience and subject stay exactly as they are.

Provider URLhttps://oidc.vercel.com
Principalarn:aws:iam::YOUR_ACCOUNT_ID:oidc-provider/oidc.vercel.com
Condition keysoidc.vercel.com:aud / oidc.vercel.com:sub
Audienceunchanged — https://vercel.com/kevin-bandisons-projects
Subjectunchanged

In other words: drop /kevin-bandisons-projects from the issuer everywhere it appears, and leave the two values it isn’t part of alone. The setting is per project — Project → Settings → Security → Secure backend access with OIDC federation.

Renaming the team or project breaks this. The slug and project name are inside the sub and aud claims, so a rename silently stops the role being assumable. If you ever rename, add a second statement for the new name before switching.

Put two variables in Vercel

vercel env add AWS_REGION production
vercel env add AWS_ROLE_ARN production

Repeat for preview if you want previews to have it. That is the whole secret story: there isn’t one. AWS_ROLE_ARN only names a role, and only Vercel-signed tokens for this project can assume it.

Set AWS_REGION explicitly. It’s the one people skip, on the reasonable assumption that AWS defaults it sensibly. Vercel does default it — to its own function’s region, which is wrong for us and can change between invocations.

Both are in turbo.json’s globalEnv. They weren’t before: Turbo strips variables it doesn’t declare, and a stripped variable is indistinguishable from an unset one.

Get a token locally

The role needs no help on Vercel. Locally there is no invocation to carry a token, so pull one: 

vercel link          # if this repo isn't linked yet
vercel env pull .env.local --yes

Then add to the root .env.local:

AWS_REGION=us-east-1
AWS_ROLE_ARN=arn:aws:iam::YOUR_ACCOUNT_ID:role/noghost-app

us-east-1 is a recommendation, not a requirement — any of the five in step 1 works, and nothing needs to already exist there. Neither service has resources to be in the wrong region; the region only decides which endpoint gets called. Use the same one here as in the policy ARN and on Vercel.

Two things that have bitten this repo before. Pull to the repo root — there is one .env.local and it lives at the top; vercel link has previously recreated apps/web/.env.local, which nothing reads. And check which team you linked: it has picked the wrong team’s noghost-web before.

VERCEL_OIDC_TOKEN expires. The one you pull is a development token and lasts 12 hours — the ones Vercel mints for preview and production last two, and builds get one. When aws:check says the token is unreadable, pull again.

Check it

pnpm aws:check

This makes three real calls — a fraction of a cent — rather than checking that three variables are non-empty. A key with the wrong permissions, a region carrying neither service, and a typo in the provider ARN all look identical to a presence check.

AWS is wired up.

When something is wrong it names the variable rather than the symptom. An unknown access key, a bad secret, a refused action and a dead endpoint otherwise produce much the same unhelpful stack trace — and “the security token included in the request is invalid” means the key doesn’t exist, not that the policy refused it, which is an hour in the wrong console if you take it at face value.

If you dropped the development subject from the trust policy in step 3, this will not pass on your laptop — the token vercel env pull gives you is a development token, so STS refuses it with IDPRejectedClaim. That is the policy working. Verify on a deployment instead, or add the line back.

Then, for the real thing end to end: pnpm dev, walk /apply/start to step 3, and do the pose sequence with an actual face.

Set a billing alarm anyway. Not because these numbers are frightening, but because a loop retrying a failing call is how a fraction of a cent becomes a bill.

If you’d rather use an access key

The role is better and not much harder, but the key path still works and lib/aws.ts still supports it — AWS_ROLE_ARN simply wins when both are set, which is what makes switching safe in either direction.

IAM → Users → Create user, named noghost-app, console access unchecked, with the policy from step 2 attached. Then Security credentials → Create access key → Application running outside AWS. Copy both values; the secret is shown exactly once. Set AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY instead of AWS_ROLE_ARN.

Going from key to role later: add AWS_ROLE_ARN, run aws:check — it will say the key is being ignored — and once that is green, delete the key in IAM and drop both variables. There is no moment in between where the app cannot authenticate.
